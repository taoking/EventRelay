## Issue #8 — Delivery Domain 与持久化

### 1. 任务原文

## 目标

实现 EventRelay 的第四个正式业务能力：**Delivery 领域模型与持久化**。

Delivery 表示“一个 Event 计划投递到一个 Endpoint”的稳定业务记录：

`Event + Endpoint -> Delivery`

本 Issue 只建立 Delivery 的领域模型、持久化、内部创建用例和只读查询能力，为后续“Event 根据 Subscription 自动匹配 Endpoint 并创建 Delivery”提供可靠基础。

**本 Issue 不做自动匹配、不入 Queue、不执行 Worker、不发送任何 Webhook HTTP 请求。**

## In Scope

### 1. Delivery 领域模型

Delivery 至少包含：

- `id`：稳定、不可变的公开 UUID v4；API 不暴露数据库自增 ID。
- `eventId`：关联既有 Event 的公开领域 ID。
- `endpointId`：关联既有 Endpoint 的公开领域 ID。
- `status`：本 Issue 新建 Delivery 一律为 `pending`。
- `createdAt`。
- `updatedAt`。

Delivery 创建后，本 Issue 不提供状态迁移行为；成功/失败/重试等状态变化留给后续投递 Issue。可以引入纯 Domain `DeliveryStatus` 值对象/枚举，也可以采用其他同等清晰的设计；不要把 Laravel/Eloquent 类型带入 Domain。

### 2. 一个 Event + Endpoint 只能对应一个 Delivery

这是本轮最重要的不变量：`unique(event_id, endpoint_id)`。

同一个 Event 对同一个 Endpoint 不能因为重复调用、任务重试或并发竞争创建多个 Delivery。

要求：

- DB 层必须有唯一约束；
- Application/Infrastructure 创建路径必须具有**幂等语义**：重复请求同一 Event + Endpoint 时返回既有 Delivery，而不是创建第二条；
- 不能只依赖“先 SELECT 再 INSERT”的脆弱 check-then-insert；必须让数据库唯一约束成为最终并发防线，并正确处理竞争结果；
- 不要求本 Issue 建立通用 Idempotency-Key 系统。

### 3. Application 创建用例

新增内部 Application 能力，例如 `CreateDelivery`（具体命名由 Agent 决定）。输入为 Event public ID 和 Endpoint public ID。

行为：

1. Event 必须存在；不存在返回明确的 Application/business not-found 语义；
2. Endpoint 必须存在且未 soft delete；否则返回明确的 Application/business not-found 语义；
3. 创建一个 `pending` Delivery；
4. 同一 Event + Endpoint 重复调用返回同一个 Delivery；
5. 不检查 Subscription；Subscription 匹配属于下一轮；
6. 本 Issue 不定义 disabled Endpoint 是否参与未来自动匹配，该策略留给匹配 Issue。

**不要公开 `POST /api/deliveries`。** Delivery 的创建当前只是供未来匹配流程调用的内部 Application 能力，避免暴露一个可以绕过 Subscription 的公共创建接口。

### 4. Delivery 只读 API

实现 `GET /api/deliveries` 和 `GET /api/deliveries/{id}`。成功响应沿用现有 `{ "data": ... }` envelope，至少返回：

```json
{
  "id": "delivery-public-uuid",
  "event_id": "event-public-uuid",
  "endpoint_id": "endpoint-public-uuid",
  "status": "pending",
  "created_at": "...",
  "updated_at": "..."
}
```

要求：列表顺序稳定、可测试；未知 Delivery 返回 404；本 Issue 不提供 Delivery POST/PATCH/DELETE HTTP API。

### 5. 持久化

新增 `deliveries` 持久化结构。最低要求：

- `public_id` 唯一；
- 关联 Event 内部 FK；
- 关联 Endpoint 内部 FK；
- `status` 有合理长度约束，不使用不易演进的数据库 ENUM；
- `(event_id, endpoint_id)` 唯一；
- migration 可从 fresh database 成功执行；
- Delivery 历史不得因为 Endpoint 的订阅清空而删除；
- Delivery 历史不得采用 `cascadeOnDelete` 这种会把历史投递随 Endpoint/Event 物理删除的设计。对于 Delivery 这类历史记录，应优先使用限制/保留语义；具体 FK 写法由 Agent 根据当前 schema 决定并说明。

Endpoint 当前使用 soft delete，因此正常删除 Endpoint 后历史 Delivery 行应仍可保留和读取。

### 6. 分层要求

继续遵守现有架构：

- Domain 不依赖 Laravel / Eloquent / DB / Redis / Queue / HTTP Client；
- Controller 不直接访问 Eloquent/DB；
- HTTP → Application → Domain；
- Infrastructure 实现 Delivery 持久化；
- 复用既有 `EventId`、`EndpointId`、Shared UUID 能力，禁止复制 UUID 规则；
- Infrastructure 异常不得无意泄漏成业务 500；
- 不得弱化 Deptrac、PHPStan、Tests 或既有 Acceptance Criteria。

### 7. 测试

至少覆盖：

- Delivery Domain 创建时生成 UUID v4；
- 新 Delivery 默认 `pending`；
- reconstitute 保留 ID/关联/status/时间；
- 使用存在的 Event + Endpoint 创建 Delivery 成功；
- 同一 Event + Endpoint 重复创建返回同一 Delivery public ID；
- DB 中最终只有一条对应关系；
- DB 唯一约束能阻止重复关系；
- 不存在 Event 时明确失败；
- 不存在或 soft-deleted Endpoint 时明确失败；
- `GET /api/deliveries` 正常返回稳定列表；
- `GET /api/deliveries/{id}` 正常返回详情；
- 未知 Delivery 返回 404；
- Delivery 没有 POST/PATCH/DELETE 公共 API；
- Endpoint soft delete 后，已经存在的 Delivery 历史仍可读取；
- **创建 Event 即使存在匹配 Subscription，本 Issue 也不得自动创建 Delivery**，用回归测试锁住 Out of Scope；
- 现有 Endpoint/Event/Subscription 测试全部继续 PASS；
- Domain → Framework 的负向架构 Gate 继续有效。

如果实现采用数据库原子 create-or-return-existing 策略，应为其竞争/重复路径增加有意义的测试，而不是只测 happy path。

## 二、本轮核心目标

## 三、最重要的不变量

同一个 Event + Endpoint 只能存在一个 Delivery。数据库必须建立 `unique(event_id, endpoint_id)`；Application / Infrastructure 创建路径必须具备幂等语义：第一次调用创建 Delivery A，第二次相同 Event + Endpoint 返回 Delivery A，而不是创建 Delivery B。不能只使用 `SELECT → 没有 → INSERT` 这种存在并发竞态的简单 check-then-insert。数据库唯一约束必须成为最终并发防线，并正确处理重复创建竞争。本 Issue 不需要实现通用 Idempotency-Key。

## 四、Delivery Domain

至少包含 public UUID v4 id、EventId、EndpointId、status、createdAt、updatedAt。本 Issue 新建 Delivery 状态固定为 `pending`，不得实现 succeeded / failed / retry 等真实投递状态迁移行为。Domain 必须保持 Framework-independent，禁止依赖 Laravel、Eloquent、DB、Redis、Queue、HTTP Client。复用现有 EventId、EndpointId、Shared UUID，不得重新复制 UUID 逻辑。

## 五、创建 Delivery

建立内部 Application Use Case，例如 CreateDelivery。输入为 Event public ID、Endpoint public ID。行为：

1. Event 必须存在；
2. Endpoint 必须存在且未 soft delete；
3. 创建 pending Delivery；
4. 相同 Event + Endpoint 重复调用返回同一 Delivery；
5. 不检查 Subscription；
6. 不做自动匹配。

不存在 Event / Endpoint 必须转换成明确 Application/business not-found 语义。不得让 Eloquent ModelNotFoundException、QueryException 等 Infrastructure 细节意外泄漏成 HTTP 500。

不得公开 POST /api/deliveries。禁止实现 `POST /api/deliveries`，因为当前 Delivery 创建是内部 Application 能力。未来 `Event → Subscription Match → CreateDelivery` 会调用它；现在公开 POST Delivery 会形成绕开 Subscription 的公共后门。

## 七、只读 API

实现 GET `/api/deliveries`、GET `/api/deliveries/{id}`。响应继续使用 `{ "data": ... }`，至少返回 id、event_id、endpoint_id、status、created_at、updated_at。要求：public ID，不暴露内部 DB ID；列表顺序稳定；未知 Delivery 返回 404；不提供 Delivery PATCH、DELETE、POST。

## 八、历史保留

Delivery 是历史业务记录。因此不要使用会导致历史数据随 Endpoint/Event 物理删除而级联消失的 `cascadeOnDelete` 设计。Endpoint 当前是 soft delete。Delivery 创建成功后，Endpoint soft delete → Delivery 仍然存在 → GET Delivery 仍然可以读取历史记录。但是 soft-deleted Endpoint → 不允许再创建新的 Delivery。

## 二、问题说明

当前 `EloquentDeliveryRepository::createOrGet()` 大致流程：

```text
DB transaction
    ↓
普通 SELECT Event
    ↓
SELECT Endpoint FOR UPDATE
    ↓
INSERT Delivery
    ↓
unique(event_id, endpoint_id) 冲突
    ↓
catch QueryException
    ↓
普通 SELECT existing Delivery
```

MySQL / InnoDB 默认使用 `REPEATABLE READ`。同一事务中的普通 consistent SELECT 会复用第一次普通 SELECT 建立的 snapshot。因此可出现：事务 B 先 `SELECT Event` 建立 snapshot；事务 A 创建并提交 Delivery；事务 B 获取 Endpoint lock 后 INSERT 撞唯一键；事务 B catch 后普通查询 existing Delivery 仍读取旧 snapshot，得到 `null` 并泄漏 `QueryException`。

## 三、本轮目标

修复“同一 Event + Endpoint 真正并发创建 Delivery 时，所有调用都成功获得同一个 Delivery”。必须满足：并发 A 与 B 均 success、`A.delivery_id == B.delivery_id`、数据库对应 Delivery count 为 1。
