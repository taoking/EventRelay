## Issue #8 — Delivery Domain 与持久化

### 1. 任务原文

## 目标

实现 EventRelay 的第四个正式业务能力：**Delivery 领域模型与持久化**。

Delivery 表示“一个 Event 计划投递到一个 Endpoint”的稳定业务记录：

`Event + Endpoint -> Delivery`

本 Issue 只建立 Delivery 的领域模型、持久化、内部创建用例和只读查询能力，为后续“Event 根据 Subscription 自动匹配 Endpoint 并创建 Delivery”提供可靠基础。

**本 Issue 不做自动匹配、不入 Queue、不执行 Worker、不发送任何 Webhook HTTP 请求。**

## In Scope

### 1. Delivery 领域模型

Delivery 至少包含：

- `id`：稳定、不可变的公开 UUID v4；API 不暴露数据库自增 ID。
- `eventId`：关联既有 Event 的公开领域 ID。
- `endpointId`：关联既有 Endpoint 的公开领域 ID。
- `status`：本 Issue 新建 Delivery 一律为 `pending`。
- `createdAt`。
- `updatedAt`。

Delivery 创建后，本 Issue 不提供状态迁移行为；成功/失败/重试等状态变化留给后续投递 Issue。可以引入纯 Domain `DeliveryStatus` 值对象/枚举，也可以采用其他同等清晰的设计；不要把 Laravel/Eloquent 类型带入 Domain。

### 2. 一个 Event + Endpoint 只能对应一个 Delivery

这是本轮最重要的不变量：`unique(event_id, endpoint_id)`。

同一个 Event 对同一个 Endpoint 不能因为重复调用、任务重试或并发竞争创建多个 Delivery。

要求：

- DB 层必须有唯一约束；
- Application/Infrastructure 创建路径必须具有**幂等语义**：重复请求同一 Event + Endpoint 时返回既有 Delivery，而不是创建第二条；
- 不能只依赖“先 SELECT 再 INSERT”的脆弱 check-then-insert；必须让数据库唯一约束成为最终并发防线，并正确处理竞争结果；
- 不要求本 Issue 建立通用 Idempotency-Key 系统。

### 3. Application 创建用例

新增内部 Application 能力，例如 `CreateDelivery`（具体命名由 Agent 决定）。输入为 Event public ID 和 Endpoint public ID。

行为：

1. Event 必须存在；不存在返回明确的 Application/business not-found 语义；
2. Endpoint 必须存在且未 soft delete；否则返回明确的 Application/business not-found 语义；
3. 创建一个 `pending` Delivery；
4. 同一 Event + Endpoint 重复调用返回同一个 Delivery；
5. 不检查 Subscription；Subscription 匹配属于下一轮；
6. 本 Issue 不定义 disabled Endpoint 是否参与未来自动匹配，该策略留给匹配 Issue。

**不要公开 `POST /api/deliveries`。** Delivery 的创建当前只是供未来匹配流程调用的内部 Application 能力，避免暴露一个可以绕过 Subscription 的公共创建接口。

### 4. Delivery 只读 API

实现 `GET /api/deliveries` 和 `GET /api/deliveries/{id}`。成功响应沿用现有 `{ "data": ... }` envelope，至少返回：

```json
{
  "id": "delivery-public-uuid",
  "event_id": "event-public-uuid",
  "endpoint_id": "endpoint-public-uuid",
  "status": "pending",
  "created_at": "...",
  "updated_at": "..."
}
```

要求：列表顺序稳定、可测试；未知 Delivery 返回 404；本 Issue 不提供 Delivery POST/PATCH/DELETE HTTP API。

### 5. 持久化

新增 `deliveries` 持久化结构。最低要求：

- `public_id` 唯一；
- 关联 Event 内部 FK；
- 关联 Endpoint 内部 FK；
- `status` 有合理长度约束，不使用不易演进的数据库 ENUM；
- `(event_id, endpoint_id)` 唯一；
- migration 可从 fresh database 成功执行；
- Delivery 历史不得因为 Endpoint 的订阅清空而删除；
- Delivery 历史不得采用 `cascadeOnDelete` 这种会把历史投递随 Endpoint/Event 物理删除的设计。对于 Delivery 这类历史记录，应优先使用限制/保留语义；具体 FK 写法由 Agent 根据当前 schema 决定并说明。

Endpoint 当前使用 soft delete，因此正常删除 Endpoint 后历史 Delivery 行应仍可保留和读取。

### 6. 分层要求

继续遵守现有架构：

- Domain 不依赖 Laravel / Eloquent / DB / Redis / Queue / HTTP Client；
- Controller 不直接访问 Eloquent/DB；
- HTTP → Application → Domain；
- Infrastructure 实现 Delivery 持久化；
- 复用既有 `EventId`、`EndpointId`、Shared UUID 能力，禁止复制 UUID 规则；
- Infrastructure 异常不得无意泄漏成业务 500；
- 不得弱化 Deptrac、PHPStan、Tests 或既有 Acceptance Criteria。

### 7. 测试

至少覆盖：

- Delivery Domain 创建时生成 UUID v4；
- 新 Delivery 默认 `pending`；
- reconstitute 保留 ID/关联/status/时间；
- 使用存在的 Event + Endpoint 创建 Delivery 成功；
- 同一 Event + Endpoint 重复创建返回同一 Delivery public ID；
- DB 中最终只有一条对应关系；
- DB 唯一约束能阻止重复关系；

- `GET /api/deliveries` 正常返回稳定列表；
- `GET /api/deliveries/{id}` 正常返回详情；
- 未知 Delivery 返回 404；
- Delivery 没有 POST/PATCH/DELETE 公共 API；
- Endpoint soft delete 后，已经存在的 Delivery 历史仍可读取；
- **创建 Event 即使存在匹配 Subscription，本 Issue 也不得自动创建 Delivery**，用回归测试锁住 Out of Scope；

如果实现采用数据库原子 create-or-return-existing 策略，应为其竞争/重复路径增加有意义的测试，而不是只测 happy path。

## 二、本轮核心目标

## 三、最重要的不变量

同一个 Event + Endpoint 只能存在一个 Delivery。数据库必须建立 `unique(event_id, endpoint_id)`；Application / Infrastructure 创建路径必须具备幂等语义：第一次调用创建 Delivery A，第二次相同 Event + Endpoint 返回 Delivery A，而不是创建 Delivery B。不能只使用 `SELECT → 没有 → INSERT` 这种存在并发竞态的简单 check-then-insert。数据库唯一约束必须成为最终并发防线，并正确处理重复创建竞争。本 Issue 不需要实现通用 Idempotency-Key。

## 四、Delivery Domain

至少包含 public UUID v4 id、EventId、EndpointId、status、createdAt、updatedAt。本 Issue 新建 Delivery 状态固定为 `pending`，不得实现 succeeded / failed / retry 等真实投递状态迁移行为。Domain 必须保持 Framework-independent，禁止依赖 Laravel、Eloquent、DB、Redis、Queue、HTTP Client。复用现有 EventId、EndpointId、Shared UUID，不得重新复制 UUID 逻辑。

## 五、创建 Delivery

建立内部 Application Use Case，例如 CreateDelivery。输入为 Event public ID、Endpoint public ID。行为：

1. Event 必须存在；
2. Endpoint 必须存在且未 soft delete；
3. 创建 pending Delivery；
4. 相同 Event + Endpoint 重复调用返回同一 Delivery；
5. 不检查 Subscription；
6. 不做自动匹配。

不存在 Event / Endpoint 必须转换成明确 Application/business not-found 语义。不得让 Eloquent ModelNotFoundException、QueryException 等 Infrastructure 细节意外泄漏成 HTTP 500。

不得公开 POST /api/deliveries。禁止实现 `POST /api/deliveries`，因为当前 Delivery 创建是内部 Application 能力。未来 `Event → Subscription Match → CreateDelivery` 会调用它；现在公开 POST Delivery 会形成绕开 Subscription 的公共后门。

## 七、只读 API

## 八、历史保留

Delivery 是历史业务记录。因此不要使用会导致历史数据随 Endpoint/Event 物理删除而级联消失的 `cascadeOnDelete` 设计。Endpoint 当前是 soft delete。Delivery 创建成功后，Endpoint soft delete → Delivery 仍然存在 → GET Delivery 仍然可以读取历史记录。但是 soft-deleted Endpoint → 不允许再创建新的 Delivery。

## 二、问题说明

当前 `EloquentDeliveryRepository::createOrGet()` 大致流程：

```text
DB transaction
    ↓
普通 SELECT Event
    ↓
SELECT Endpoint FOR UPDATE
    ↓
INSERT Delivery
    ↓
unique(event_id, endpoint_id) 冲突
    ↓
catch QueryException
    ↓
普通 SELECT existing Delivery
```

MySQL / InnoDB 默认使用 `REPEATABLE READ`。同一事务中的普通 consistent SELECT 会复用第一次普通 SELECT 建立的 snapshot。因此可出现：事务 B 先 `SELECT Event` 建立 snapshot；事务 A 创建并提交 Delivery；事务 B 获取 Endpoint lock 后 INSERT 撞唯一键；事务 B catch 后普通查询 existing Delivery 仍读取旧 snapshot，得到 `null` 并泄漏 `QueryException`。

## 三、本轮目标

#### 3. 根因分析

## In Scope

### 1. Event 创建后自动匹配 Subscription

现有 `POST /api/events` 成功创建 Event 后，需要根据该 Event 的 `EventType` 查找当前匹配的 Endpoint Subscription。

匹配规则：

- 只做 **exact match**；
- `order.paid` 只匹配订阅 `order.paid`；
- 不支持 wildcard；
- 不支持 prefix；
- 不支持 topic pattern；
- 不新增第二套 Event type 规则，继续复用现有 `EventType` Domain Value Object。

禁止通过：

```text
读取全部 Endpoint
→ 每个 Endpoint 再查 subscriptions
→ PHP 内存中过滤
```

这种 N+1 / 全表扫描方式实现匹配。

应提供清晰的 Application contract + Infrastructure 查询能力，直接从持久化层查询某个 EventType 当前符合条件的 Endpoint IDs。

### 2. 只有 active + 未 soft delete Endpoint 才能匹配

本 Issue 正式确定自动匹配策略：

```text
Endpoint status=active
AND deleted_at IS NULL
AND subscription.event_type == event.type
→ eligible
```

以下 Endpoint 不得生成新的 Delivery：

- `disabled` Endpoint；
- soft-deleted Endpoint；
- 没有订阅该 Event type 的 Endpoint。

Endpoint 后续被 disabled / soft delete，不删除已经形成的 Delivery 历史。

### 3. 为每个匹配 Endpoint 复用既有 CreateDelivery

匹配结果不能自己重新 INSERT Delivery。

必须复用 Issue #8 已经验证过的内部 Delivery 创建能力及其不变量：

- Delivery 默认 `pending`；
- `unique(event_id, endpoint_id)`；
- 重复/竞争创建返回同一 Delivery；
- soft-deleted Endpoint 不能创建；
- Infrastructure 异常不能错误泄漏。

不要复制第二套 Delivery 创建逻辑。

### 4. Event + Matching + Delivery 必须具备原子业务语义

当前仍是单 MySQL 数据库，因此本轮要求把：

```text
保存 Event
+
读取本次匹配 Subscription
+
创建所有匹配 Delivery
```

视为一个完整业务操作。

不能出现：

```text
Event 已经 201 / 已持久化
但 3 个匹配 Endpoint 只创建了 1 个 Delivery
```

如果在自动匹配 / Delivery 创建过程中发生**未被业务规则正常吸收的异常**，本轮 Event + 本轮生成的 Delivery 必须整体回滚，不能留下 partial delivery set。

允许增加一个最小的 Application transaction / UnitOfWork contract，并由 Infrastructure/Laravel 实现；也允许其他同等清晰、可测试的事务边界设计。

不要把 `DB::transaction()` 直接塞进 HTTP Controller。

### 5. 匹配集合在创建期间必须保持一致

要避免：

```text
先匹配到 active Endpoint
→ 还没 CreateDelivery
→ Endpoint 被并发 soft delete / disable
→ 本轮只产生部分、不确定结果
```

Agent 需要明确设计“本轮匹配的线性化点/一致性边界”。

可采用数据库 locking/current-read 策略，让匹配到的 subscription / endpoint eligibility 在本次 Event 事务完成前保持稳定；如果采用锁，必须：

- 使用稳定顺序，例如按 Endpoint 内部 ID 排序；
- 说明锁住哪些行；
- 说明为何不会重新引入明显死锁顺序；
- 不要全局修改 isolation level。

也可采用其他可靠方案，但必须在开发记录解释并有测试证据。

### 6. HTTP Event API 对外契约保持兼容

`POST /api/events` 仍然：

- 成功返回 `201`；
- 返回当前 Event 的 `{ "data": ... }`；
- 不需要在响应里增加 Delivery list / delivery_count；
- 不公开 Delivery 创建 API。

自动生成的 Delivery 通过现有：

- `GET /api/deliveries`
- `GET /api/deliveries/{id}`

查询。

### 7. Subscription 只影响未来 Event

匹配发生在 Event 创建时。

要求：

```text
Event E1 创建时 Endpoint A 已订阅
→ E1 有 Delivery(A)

之后清空 A 的 subscription
→ E1 的历史 Delivery 不删除

再创建 Event E2
→ E2 不再生成 Delivery(A)
```

反向也一样：

```text
E1 创建时没有订阅
→ E1 不生成 Delivery

之后新增 subscription
→ 不追溯 E1

E2 创建
→ E2 才生成 Delivery
```

本 Issue 不做历史事件 replay/backfill。

### 8. 重复 HTTP Event 请求的语义

本 Issue **不实现 API Idempotency-Key**。

因此两次独立：

`POST /api/events`

即使 type/payload 完全相同，也会生成两个不同 Event；每个 Event 都各自根据 Subscription 生成自己的 Delivery。

不要错误地跨 Event 去重 Delivery。

Delivery 唯一性仍然只针对：

`同一个 event_id + endpoint_id`

## 建议架构

允许 Agent 根据现有代码命名调整，但建议保持类似：

```text
HTTP StoreEventRequest / EventController
        ↓
Application CreateEvent / IngestEvent
        ↓
Application Transaction Boundary
        ├─ EventRepository::save
        ├─ SubscriptionMatcher::matchingActiveEndpointIds(EventType)
```

## 三、本轮目标

只实现：

**Event 创建后，根据 Subscription 自动生成 Delivery。**

完整流程：

```text
POST /api/events
    ↓
创建并保存 Event
    ↓
根据 EventType 查询匹配 Subscription
    ↓
筛选：
Endpoint.status = active
AND deleted_at IS NULL
    ↓
对每个匹配 Endpoint
调用既有 CreateDelivery
    ↓
生成 pending Delivery
```

本轮结束后：

EventRelay 第一次具备：

```text
Event
  ↓
Subscription
  ↓
Delivery
```

闭环。

但依然：

**不 Queue、不 Worker、不发 Webhook。**

## 四、Subscription 匹配规则

只支持：

**EventType exact match**

例如：

```text
order.paid
只匹配
order.paid
```

禁止本轮实现：

* wildcard
* `order.*`
* prefix
* regex topic
* routing key
* pattern subscription

继续复用现有：

`App\Domain\Event\EventType`

禁止复制第二套 Event type regex / validation。

---

## 五、匹配 Endpoint 的资格

只有：

```text
Subscription event_type == Event.type
AND Endpoint.status == active
AND Endpoint.deleted_at IS NULL
```

才允许生成 Delivery。

所以：

```text
active + subscribed
→ MATCH

disabled + subscribed
→ NO MATCH

soft deleted + subscribed
→ NO MATCH

active + not subscribed
→ NO MATCH
```

Endpoint 后续 disabled / soft delete：

**不得删除已经生成的 Delivery 历史。**

---

## 六、禁止 N+1 匹配

禁止：

```text
读取全部 Endpoint
↓
循环 Endpoint
↓
每个 Endpoint 再查 subscriptions
↓
PHP 中判断是否匹配
```

应增加清晰的 Application 查询 Contract，例如：

`SubscriptionMatcher`

或其他符合当前架构的名字。

Infrastructure 应直接查询：

```text
endpoint_subscriptions
JOIN endpoints
```

得到当前 EventType 符合资格的 Endpoint IDs。

结果必须：

* 去重；
* 稳定排序；
* 可测试。

不要为了复用强行污染当前 `EndpointSubscriptionRepository`，如果独立 Matcher Contract 更清晰，可以新增。

## 八、最重要：Event + Match + Delivery 必须原子

当前仍然是：

**单 MySQL 数据库。**

所以：

```text
Event save
+
Subscription match
+
Delivery create × N
```

必须作为一个完整事务处理。

禁止产生：

```text
Event 已保存

Subscription 匹配到：
A
B
C

Delivery：
A 成功
B 成功
C 失败

最终数据库：
Event 存在
A/B Delivery 存在
C 不存在
```

这种 partial state。

正确行为：

如果出现未被业务逻辑正常吸收的异常：

```text
Event
+
本轮全部新 Delivery
```

整体 rollback。

可以新增最小的：

```text
Application TransactionManager
或
UnitOfWork
```

由 Infrastructure/Laravel 实现。

也允许其他清晰设计。

但禁止：

`DB::transaction()` 写进 Controller。

Controller 仍然只负责 HTTP → Application。

还要处理一个重要并发窗口：

```text

↓
```

必须明确本轮匹配的一致性边界。

```text

+
```

## 十一、Subscription 只影响未来 Event

必须实现：

```text
Endpoint A 已订阅 order.paid

创建 Event E1
→ Delivery(E1,A)

随后删除 A 的 subscription

已有：
Delivery(E1,A)
必须保留
```

反向：

```text

→ 不回填 E1

创建 E2
→ 生成 Delivery(E2,A)
```

本轮禁止 replay / backfill。

## 十二、重复 POST Event 的语义

本轮没有：

`Idempotency-Key`

所以：

两次完全相同：

`POST /api/events`

仍然代表：

**两个不同 Event。**

例如：

```text
POST #1
→ Event E1
→ Delivery(E1,A)

POST #2
→ Event E2
→ Delivery(E2,A)
```

其中：

```text
E1 != E2
```

这是正确行为。

不要跨 Event 去重。

Delivery 唯一规则仍然只是：

```text
same Event
+
same Endpoint
→ one Delivery
```

### 3. 实施摘要

- 新增 Application `SubscriptionMatcher` 与 `TransactionManager` contract，并由 Eloquent/MySQL 实现及 ServiceProvider 绑定。

- 新增 Subscription `event_type, endpoint_id` lookup index，避免按 Event type 匹配时的全表扫描；没有修改 Delivery 唯一约束或其并发恢复实现。
- 新增 Feature、事务原子性、MySQL 两连接锁一致性测试；README 更新为当前自动匹配行为。

### 4. Matching、事务与并发设计

#### Matching 与资格

- `EloquentSubscriptionMatcher` 对 `endpoint_subscriptions JOIN endpoints` 进行 exact `event_type` 查询，不读取全部 Endpoint，也不做逐 Endpoint subscription 查询。
- 查询条件为 `endpoint_subscriptions.event_type = EventType`、`endpoints.status = active`、`endpoints.deleted_at IS NULL`；因此 disabled、soft-deleted 或 type 不同 Endpoint 不会进入集合。
- 使用新增 `(event_type, endpoint_id)` 索引，按 `endpoints.id` 稳定排序。结果以 public ID 去重后转换为 `EndpointId`，即使持久化异常重复也不会让 Application 循环重复调用。
- Event type 直接从 Event 所持有的既有 `EventType` 值对象取得；没有复制 regex 或 validation。

#### 事务原子性与 CreateDelivery 复用

- `CreateEvent` 通过 Application `TransactionManager` 执行“Event save + matching + CreateDelivery × N”。Infrastructure 的 `EloquentTransactionManager` 仅在 Infrastructure 使用 Laravel `DB::transaction()`；Controller 不直接控制事务。
- `CreateDelivery` 完全复用，没有新 Delivery INSERT、pending/唯一性/soft-delete/REPEATABLE READ recovery 逻辑。其内部 transaction 在外层 Event transaction 中是 savepoint；任何未吸收异常向外传播，回滚 Event 和此前已创建的 Delivery。
- 原子性回归以两个真实 Endpoint 模拟：第一个 Delivery 经真实 `CreateDelivery` 成功，第二次 repository 调用强制抛出 `RuntimeException`；最终 `events=0`、`deliveries=0`。

#### 线性化点、锁与死锁取舍

- 线性化点是 `SubscriptionMatcher` 的 MySQL `SELECT ... FOR UPDATE` JOIN current read。它读取此刻已提交的 exact subscription，并锁住匹配的 active、未删除 Endpoint 行及关联的匹配 subscription records，直至外层 Event transaction 完成。
- 与 matcher 并发的 disable/soft-delete 必须等待锁释放；若 disable/soft-delete 已先取得锁，matcher 会等待并在 current read 中观察其新资格，因而不将该 Endpoint 纳入本轮 Delivery set。subscription 变化在该线性化点之后只影响后续 Event，不回填或删除历史。
- 匹配集合按 Endpoint internal ID 升序，新的索引也以 exact event_type 后 endpoint_id 支持稳定访问。每个后续 `CreateDelivery` 重新锁同一 Endpoint 行，属同一事务重入；多个 Event match 都按相同顺序取得多行锁，避免了反向顺序造成的明显 deadlock。没有全局修改 isolation level。
- MySQL 两连接测试让 matcher 先锁住匹配 Endpoint，再让独立 updater 的 disable 因 lock wait timeout `1205` 被拒绝；随后当前 transaction 成功创建 Event/Delivery 并提交，证明 match 与 create 之间不会因该资格变化形成不受控 partial set。

### 1. Issue #12 完整任务原文

## 目标

在现有 `Event → Subscription → pending Delivery` 闭环之后，引入 EventRelay 的第一层异步执行基础设施：

```text
POST /api/events
    ↓
MySQL transaction
    ↓
Event + pending Delivery commit
    ↓
Laravel Queue / Redis
    ↓
ProcessDeliveryJob
    ↓
Application ProcessPendingDelivery
```

本 Issue 只负责 **pending Delivery 的异步入队、Redis Queue、Worker 消费骨架以及人工恢复入队能力**。

**本 Issue 不发送 Webhook HTTP，不创建 DeliveryAttempt，不改变 Delivery 为 succeeded/failed，不实现业务 Retry/Backoff/DLQ。**

## 核心语义

### 1. MySQL 是事实源，Redis 只是调度通道

Delivery 已经在 MySQL 中可靠持久化，并保持 `pending`。

Redis Queue 只表达：

> “请 Worker 尝试处理这个已经存在的 Delivery。”

Redis 中的 Job 不是 Delivery 本身，也不能成为唯一业务事实。

因此 Job payload 只携带：

- Delivery public UUID。

禁止把以下内容完整序列化进 Job：

- Eloquent Delivery model；
- Event payload；
- Endpoint model；
- Webhook URL snapshot；
- 未来 secret；
- 整个 Domain object graph。

Worker 必须根据 Delivery UUID 重新从 Application/Repository 获取当前业务记录。

### 2. 必须 commit 后再入队

绝对禁止：

```text
BEGIN MySQL transaction
→ INSERT Event
→ INSERT Delivery
→ PUSH Redis Job
→ 后续 SQL 失败
→ ROLLBACK MySQL
```

否则 Redis Worker 可能拿到一个根本不存在、最终被回滚的 Delivery。

要求：

```text
Event + Delivery 全部 commit
        ↓
Redis enqueue
```

必须有自动测试 / Runtime Evidence 证明：

- transaction rollback 时 Redis 没有 Job；
- Redis Worker 看到 Job 时对应 Delivery 已经 committed。

可以在 Application transaction 返回后调度，也可以使用可靠的 `afterCommit` 机制；具体实现由 Agent 根据现有 `CreateEvent` / `TransactionManager` 架构选择。

### 3. 不伪装 MySQL + Redis 原子性

MySQL commit 与 Redis enqueue 跨两个系统，本 Issue **不实现 Transactional Outbox**，因此不能宣称 exactly-once / atomic publication。

必须明确承认以下窗口：

```text
MySQL Delivery 已 commit
↓
Redis 临时不可用
↓
Job publication 失败
```

本 Issue 的语义要求：

- 已成功 commit 的 Event / Delivery **不得因为 Redis enqueue 失败而被回滚或删除**；
- `POST /api/events` 不应因为 commit 后 Redis 暂时不可用而返回一个会诱导客户端重试、从而创建第二个 Event 的模糊 5xx；
- publication 失败要有结构化日志 / 可诊断证据；
- Delivery 保持 `pending`，作为后续恢复的事实源；
- 提供人工恢复入队能力。

未来单独 Issue 再通过 Transactional Outbox 消除该跨系统 publication gap。

## In Scope

### 1. Application Queue Contract

新增清晰的 Application contract，例如：

`DeliveryQueue`

或同等合理命名。

职责：

- 根据 Delivery public ID 请求异步处理；
- Application 不直接依赖 Laravel Queue / Redis facade。

Infrastructure 提供 Laravel Redis Queue 实现。

### 2. dedicated Redis queue

Delivery Job 固定使用：

- Laravel Queue connection：`redis`；
- queue name：`deliveries`。

不要混入默认队列后再依赖运行时猜测。

### 3. ProcessDeliveryJob

增加真正的 Laravel Queue Job，例如：

`ProcessDeliveryJob`

要求：

- 实现 `ShouldQueue`；
- Job payload 只保存 Delivery public UUID；
- Worker 中调用 Application use case，例如 `ProcessPendingDelivery`；
- Job 本身不直接查询 Eloquent、不发 HTTP、不写业务 SQL；
- 设置合理的有限 timeout / tries，避免无限 poison job；
- 本 Issue 不实现业务 Retry/Backoff 策略。

建议考虑 Laravel unique job 能力，以 Delivery UUID 作为唯一键，降低相同 Delivery 同时被重复入队的概率。

但必须在文档中明确：

**Queue unique lock 不是业务 exactly-once，也不能替代 Delivery 幂等 / Outbox。**

### 4. ProcessPendingDelivery Application Use Case

本轮 Worker 消费只建立 Application 执行入口。

至少：

- 根据 Delivery public ID 读取 Delivery；
- 确认 Delivery 存在；
- 确认当前为 `pending`；
- 正常结束 Worker Job。

本轮不：

- 创建 DeliveryAttempt；
- 发送 HTTP；
- 修改 succeeded / failed；
- 实现 retry 状态机。

可以记录结构化“Delivery 已进入 Worker”日志作为 Runtime Evidence，但日志不能代替业务状态。

### 5. Event 创建后的自动调度

Issue #10 创建出的每一个新的 pending Delivery，在 Event/Delivery transaction 成功提交后，需要请求 DeliveryQueue 入队。

必须继续复用既有 CreateDelivery。

不得重新创建 Delivery。

多个匹配 Endpoint：

```text
Delivery A commit
Delivery B commit
Delivery C commit
↓
commit 成功后
↓
enqueue A / B / C
```

如果 transaction rollback：

```text
Event = 0
Delivery = 0
Redis jobs = 0
```

### 6. Redis publication failure semantics

必须有明确异常边界。

仅 Redis / Queue publication 类基础设施失败允许转换为“记录失败、保留 pending Delivery、HTTP Event 仍按已提交事实返回成功”的语义。

禁止：

- catch `Throwable` 后全部吞掉；
- 把 Application bug、TypeError、数据库错误误当成 Redis 临时故障；
- Redis 失败后删除 Delivery；
- Redis 失败后重新创建 Event。

### 7. 人工恢复入队

增加一个 Console → Application 的恢复入口，例如：

`php artisan deliveries:enqueue-pending`

要求：

- Command 不直接写 Eloquent/DB；
- 调用 Application use case，例如 `EnqueuePendingDeliveries`；
- Infrastructure 查询当前 `pending` Delivery IDs；
- 使用稳定顺序；
- 支持合理 `--limit`，默认例如 100，并设置上限，避免一次扫描整个大表；
- 对每个 Delivery 调用同一 `DeliveryQueue` contract；
- 输出成功 / publication failed 数量。

由于本 Issue 尚无 Outbox / 完整状态机，该恢复命令属于 **at-least-once recovery tool**；不得宣称 exactly-once。

如果 Job 使用 Laravel unique lock，应以 Delivery UUID 去重当前已排队/执行中的同一 Delivery。

## Queue / Worker 语义

本轮正式确定：

```text
Delivery row = durable business truth
Redis Job    = transient execution request
```

Redis Job 丢失时，不允许 Delivery 一起消失。

Redis Job 重复时，不允许创建第二个 Delivery。

Worker 消费同一 Delivery 多次时，本轮 Application 入口必须保持无破坏性；后续真正 HTTP 投递 Issue 必须继续在 Delivery/Attempt 层实现幂等保护。

`POST /api/events`：

- 保持现有 `201`；

- Redis publication 临时失败时，Event/Delivery 已 commit 的事实不能被伪装成“数据库没成功”。

### 3. 实施摘要

- 新增 Application 层 `DeliveryQueue`、`ProcessPendingDelivery`、`PendingDeliveryFinder` 与 `EnqueuePendingDeliveries`；Domain 没有新增 Laravel、Redis 或 Queue 依赖。
- `CreateEvent` 仍在既有 `TransactionManager` 内创建 Event、匹配订阅并复用 `CreateDelivery`。事务闭包返回 Event DTO 与本轮新建 Delivery public IDs；**只有事务成功返回后**才逐个调用 `DeliveryQueue`。
- 新增 Infrastructure 的 Laravel/Redis publisher、固定 `redis` connection 与 `deliveries` queue 的 `ProcessDeliveryJob`、以及 `deliveries:enqueue-pending` Console → Application 恢复入口。
- Worker 只将 Delivery UUID 交给 Application `ProcessPendingDelivery` 重新读取；本 Issue 不发送 HTTP、不创建 `DeliveryAttempt`、不改变 `pending` 状态，亦不实现重试/退避/DLQ。
- `CreateEvent` 只捕获明确的 `DeliveryQueueUnavailable`，使 commit 后 Redis publication 临时故障仍返回已提交 Event 的 HTTP 201；其他异常继续传播。

### 4. Queue Architecture

```text
HTTP Controller
  ↓
CreateEvent
  ↓（TransactionManager：Event + Delivery 全部提交）
CreatedEventDeliveries（EventData + 新 Delivery UUIDs）
  ↓（commit 后）
DeliveryQueue（Application port）
  ↓
LaravelRedisDeliveryQueue（Infrastructure）
  ↓
Redis: deliveries
  ↓
ProcessDeliveryJob（仅 Delivery UUID）
  ↓
ProcessPendingDelivery（Application）
  ↓
DeliveryRepository
```

Console recovery：

```text
deliveries:enqueue-pending --limit=N
  ↓
EnqueuePendingDeliveries（Application）
  ↓
PendingDeliveryFinder（稳定 internal id 排序）
  ↓
DeliveryQueue
```

### 5. commit 后入队与事务语义

选择“事务完整返回后再调度”，而不是将 `afterCommit` callback 隐藏在持久化层。`CreateEvent` 的 transaction 闭包仅创建 Event/Delivery 并返回 `CreatedEventDeliveries`；闭包正常返回代表 MySQL 已 commit，之后才遍历 Delivery IDs 调用 Queue。故任何 Delivery 创建异常都会令 outer transaction rollback，且根本不会进入入队循环。

真实 MySQL/Redis integration test 以一个 Queue wrapper 在每次 `enqueue` 时打开独立 MySQL connection 并查验 Delivery 已可见；若未来有人把入队移回 outer transaction，独立连接看不到未提交记录，测试会失败。该测试没有以 `Queue::fake()` 代替 Redis 证据。

### 6. MySQL 事实源与 Redis 调度语义

- MySQL `deliveries` row 是 durable business truth，Redis job 只是 transient execution request。
- Redis job 重复不会创建第二个 Delivery：Delivery 的业务唯一性仍由 Issue #8 的 `unique(event_id, endpoint_id)` 和 `CreateDelivery` 并发幂等保证。
- `ShouldBeUnique`（key 为 Delivery public UUID）仅降低同一 Delivery 同时重复调度的概率，**不等同** business exactly-once、Delivery idempotency 或 Transactional Outbox。
- 本轮没有 Outbox；MySQL commit 与 Redis publication 之间仍有进程崩溃窗口。当前以 pending Delivery + `deliveries:enqueue-pending` 人工 at-least-once recovery 缓解，未来由独立 Outbox Issue 解决。

### 7. Redis publication failure 语义

`LaravelRedisDeliveryQueue` 仅把明确 Redis/Predis connection publication 异常转换为 `DeliveryQueueUnavailable`，记录 `delivery_id`、`queue=deliveries`、`connection=redis`、异常类和消息。它不 catch `Throwable`。

`CreateEvent` 只吞该已知 application exception；MySQL 已提交的 Event 与 pending Delivery 保留，HTTP 仍返回 201，以免客户端把事实成功误判为 5xx 并重复 POST 创建新的 Event。TypeError、逻辑错误、MySQL 异常及未知 RuntimeException 不会被吞掉。

### 8. Job、Worker 与恢复设计

- `ProcessDeliveryJob` 实现 `ShouldQueue` 与 `ShouldBeUnique`，connection 固定 `redis`，queue 固定 `deliveries`，`tries=1`、`timeout=10`。
- 序列化 payload 的业务字段仅为 public `deliveryId`；不含 Eloquent Model、Event payload、Endpoint 或 Endpoint URL。
- `ProcessPendingDelivery` 经 repository 查找 Delivery；不存在时抛既有业务 `DeliveryNotFound`，pending 时无副作用完成。Job consumption 后 Delivery 继续为 `pending`。
- `EloquentPendingDeliveryFinder` 按 internal `id ASC`、limit 读取 pending public IDs。恢复命令默认 100，Application 强制范围 1–1000，并输出成功/发布失败计数。
- 当前恢复为 at-least-once：已消费但仍 pending 的 Delivery 也可能被重调度；此时没有外部副作用，所以是刻意且受限的临时语义。

### 14. 为什么本轮仍存在 MySQL → Redis publication gap

```text

T2 Redis enqueue
```

#### 3. ServerException 根因与 translation 策略

Predis 的 `ConnectionException` / `StreamInitException` 表示连接建立或 I/O 失败；`Predis\Response\ServerException` 则表示已连接 Redis 的服务端对命令返回错误，例如 READONLY、OOM/maxmemory 或 `-ERR`。两者都是当前 publish request 的明确基础设施失败，但不能用宽泛的 `PredisException` 或 `Throwable` 概括，因为后者可能混入客户端配置或编程错误。

`LaravelRedisDeliveryQueue` 现在只精确捕获 ConnectionException、StreamInitException、RedisException 和 ServerException，并统一转换为 `DeliveryQueueUnavailable`、写入不含 payload 的结构化 warning。`CreateEvent` 继续只捕获该 Application exception，所以 MySQL commit 后已知 Redis 服务端错误返回 HTTP 201；未知异常仍传播。

#### 4. Laravel 13 unique dispatch 根因与方案

本地 Laravel 13.29.0 源码确认：`Illuminate\Bus\Dispatcher::dispatch()` 仅将 `ShouldQueue` Job push 到 queue，不获取 `ShouldBeUnique` lock；`Illuminate\Foundation\Bus\PendingDispatch::__destruct()` 的 `shouldDispatch()` 先经 `UniqueLock::acquire()` 获得 Delivery UUID lock，再委派 dispatcher。

publisher 现在创建同一 `ProcessDeliveryJob` 实例，再使用 `PendingDispatch` 并显式销毁它，使 Laravel 标准 unique-lock 路径实际执行。connection/queue、payload、Worker Application 边界均保持不变。

#### 5. unique lock 与 publication failure cleanup

若 PendingDispatch 已获得 lock 而 dispatcher 的 Redis publication 失败，publisher 对上述精确 Redis failure 调用 `UniqueLock::release($job)`。使用同一 Job 实例可保留 Laravel 写入的 unique lock owner，故只释放该次 publication 的 lock。cleanup 中也只忽略相同的明确 Redis 基础设施异常；任何未知 cleanup 异常继续传播，避免宽泛吞错。

这样 Redis 恢复后，`EnqueuePendingDeliveries` 可立即再取得 lock 并真正写入 queue，不必等待 `uniqueFor=60`。这仍只是 queue 调度优化，不是 exactly-once、业务 Delivery 幂等或 Outbox。
