# 架构原则

## 总体形式

EventRelay 第一阶段采用**模块化单体**，不做微服务。

建议依赖方向：

```text
HTTP -> Application -> Domain
Infrastructure -> Domain/Application contracts
```

## 强制原则

1. Domain 不依赖 Laravel Framework。
2. Domain 不依赖 Eloquent、Redis、Queue、HTTP Client。
3. Controller 不承载业务规则。
4. Controller 不直接访问 Redis、Queue、第三方 HTTP Client。
5. 数据访问通过明确的 Application/Repository 边界完成。
6. Infrastructure 负责框架、数据库、队列、网络等实现细节。
7. 公共能力只有一个权威实现，禁止各模块重复造 Helper。
8. 新依赖必须说明必要性。
9. 架构规则能机械验证的，优先写成 Deptrac/测试，而不是只写文档。

## 禁止事项

- 为“未来可能需要”提前引入微服务。
- 未经架构 Issue 批准的大规模跨层重构。
- Domain 中直接使用 Facade。
- 让 Controller 逐渐变成 Service。
- 使用 `Utils`、`CommonHelper` 等无明确职责的万能模块。

## 架构变更

若变化涉及数据库 Schema、公开 API、核心依赖方向、模块拆分，必须先建立 Architecture/Tech Debt Issue，再拆成小 PR 执行。
